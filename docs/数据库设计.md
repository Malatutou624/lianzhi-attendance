# 数据库设计说明书（零基础版）

数据库名：`lianzhi_attendance`，共 **7 张表**。

## 一、表之间的关系（一句话版）

```
sys_user        管理员登录用的，和其他表没关系
venue (场所) 1 ──── n  employee (员工)     一个场所下有多个员工
venue (场所) 1 ──── 1  attend_rule (规则)  每个场所一条考勤规则
employee 1 ──── n checkin_record (打卡)    一个员工每天多条打卡记录
employee 1 ──── n leave_apply (请假)       一个员工多张申请单
venue + checkin_record ──(定时任务汇总)──> daily_stats 每日统计
```

## 二、逐表讲解（面试能讲出这些就够用）

| 表名 | 干什么用 | 关键字段 |
|---|---|---|
| sys_user | 管理端登录 | username/password（MD5 加密） |
| venue | 办公场所登记，支持总部-子公司层级 | parent_id 层级、longitude/latitude 地图坐标、radius 打卡范围 |
| employee | 员工信息，H5 扫码采集写入 | face_photo 人脸照片、face_feature 虹软特征值 |
| checkin_record | **核心表**，每次打卡一条流水 | similarity 人脸相似度、status 迟到判定、建立 3 个索引加速查询 |
| attend_rule | 每个场所的上下班时间 | work_start/work_end/late_minutes |
| daily_stats | 每天每个场所一行汇总数据 | 由 Spring Task 定时从 checkin_record 统计生成 |
| leave_apply | 请假/加班申请审批 | status 流转：pending→approved/rejected |

## 三、数据流（扫码打卡全链路，面试必考）

1. 管理员在管理端登记场所 → 写入 `venue`
2. 系统为该场所生成二维码（内容含 venueId）→ 员工手机扫码
3. 员工在 H5 页填写信息 + 拍人脸照 → 写入 `employee`（face_photo/face_feature）
4. 员工每天扫码打开 H5 打卡页 → 拍照 → 后端调虹软 SDK 与 face_feature 比对
5. 比对通过 → 写入 `checkin_record`，同时根据 `attend_rule` 判断是否迟到
6. 每天凌晨 Spring Task 统计 `checkin_record` → 写入 `daily_stats`
7. 数据看板读取 `daily_stats` + 当日 `checkin_record` 实时数据 → ECharts 展示

## 四、为什么这么设计（答辩加分点）

- **打卡记录是流水表，只增不改**：数据量大，所以给 (emp_id, checkin_time) 建了联合索引
- **统计表和流水表分离**：看板查 daily_stats 不用每次扫全量流水，这是性能优化的常规手段
- **face_feature 用 TEXT**：虹软特征值约 1-2KB 的 Base64 字符串，TEXT 足够
- **密码 MD5 存储**：数据库泄露也看不到明文（答辩可提：生产环境应换 BCrypt）
